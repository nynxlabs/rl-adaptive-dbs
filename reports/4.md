## Compute upgrade: AMD Ryzen 7 5800X (8c/16t) → Ryzen 9 5900XT (16c/32t)

Report 3 listed a workstation compute upgrade as upcoming work. That upgrade is **done** (August 2026): the training workstation CPU is now an **AMD Ryzen 9 5900XT** (**16 cores / 32 threads**), replacing the previous **AMD Ryzen 7 5800X** (**8 cores / 16 threads**) that carried all replication trains since Report 1.

### Why it matters for this project

**One train at a time is not much faster.** Each replication run is single-threaded (`OMP_NUM_THREADS=1`), and because integrating the biophysical network equations is pure floating-point math, one simulation run fully saturates a physical core. A single 500-episode training run still takes roughly the same wall-clock time; the upgrade buys **dedicated physical core concurrency and parallel sweep capacity**, not faster individual trains.

| Area | Before: Ryzen 7 5800X (8 cores / 16 threads) | Now: Ryzen 9 5900XT (16 cores / 32 threads) |
|------|-----------------------------------------------|---------------------------------------------|
| **Parallel worker capacity** | Reserving 2-4 cores for the OS and tooling left **4-6 concurrent simulation workers** max. A 4-variant ablation panel consumed nearly all available capacity. | Reserving 2-4 cores for the OS and tooling leaves **12-14 dedicated simulation workers** running at 100% full speed without SMT thread contention. |
| **Multi-seed / ablation sweeps** | Running a 4-variant ablation across 3 seeds (12 runs total) required queuing across multiple serial batches. | Running an entire 12-run sweep (e.g., all 4 ablation variants across 3 seeds simultaneously) in a single parallel batch. |
| **Multitasking & eval** | Running continuous parameter sweeps alongside local evaluation and plotting scripts caused sluggishness and process contention. | **Headroom to spare**: keep 12 full simulation sweeps running in the background while compiling figures, analyzing data, and running local tools. |
| **Calendar throughput** | Multi-candidate tuning was bottlenecked by serial execution lanes. | More parallel lanes mean significantly more completed hyperparameter experiments per week. |

## Reproducibility & run commands

Full per-panel replication commands and gate specifications live in the repository figure trackers:
- [figures/mehregan/replications.md](https://github.com/wilzen3476/rl-adaptive-dbs/blob/main/figures/mehregan/replications.md)
- [figures/nguyen/replications.md](https://github.com/wilzen3476/rl-adaptive-dbs/blob/main/figures/nguyen/replications.md)
- [figures/ravivarapu/replications.md](https://github.com/wilzen3476/rl-adaptive-dbs/blob/main/figures/ravivarapu/replications.md)

```bash
git clone https://github.com/wilzen3476/rl-adaptive-dbs.git
cd rl-adaptive-dbs

# Mehregan Fig. 4a (DDPG 45 Hz training beta vs step)
uv run python -m rl_adaptive_dbs.run scripts/figures/papers/mehregan/4a/plot.py

# Ravivarapu Fig. 7 (4-variant ablation sweep at 50 Hz)
uv run python -m rl_adaptive_dbs.run scripts/figures/papers/ravivarapu/7/plot.py

# Replot any panel from cached simulation series without re-training
uv run python -m rl_adaptive_dbs.run scripts/figures/papers/ravivarapu/7/plot.py --plot-only
```

**Environment note:** All runs were executed and verified locally using `uv`. Standard installation and dependency management procedures are provided in `scripts/setup.sh` and the repository documentation. Note that while current workflows run cleanly against active local environments, end-to-end setup verification from a completely fresh system install hasn't been re-tested recently (tracked under upcoming work). Because full replication training sweeps involve computationally intensive biophysical ODE integration across multiple seeds and variants, reproducing all training sweeps from scratch takes a substantial amount of compute time and is recommended on an 8+ core workstation (cached series and checkpoints are provided in the repository to replot all panels instantly).
